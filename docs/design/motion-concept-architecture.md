# 설계안: 움직임 설계 층과 개념 어휘 층 (v0.12 ~ v0.14 제안)

상태: **승인된 범위부터 진행 중.** 결정 1·2 확정(2026-10-05, 권장안). 1단계 완료(v0.12.0). 2단계 완료(v0.14.0): 다이어그램, trend, 연쇄 장애, 흐름, 스레드 풀 이전. 결정 3·4는 3단계 전에 확인한다.
근거 자료: kciter.so "애니메이션을 설계하는 방법"(원리만 참고, 코드·그림은 옮기지 않음), 같은 사이트의 다른 글 데모,
이 저장소의 현재 코드(아래 수치는 2026-10-05 기준 실측).

---

## 1. 목표와 비목표

**목표**
1. 움직임의 질을 사례별 수정이 아니라 구조로 올린다. "끊어짐", "너무 빠름", "한꺼번에 툭 나타남"이 새 시각화에서
   처음부터 생기지 않게 한다.
2. 개념 설명(DDD, AI 에이전트, 프롬프트·맥락 같은 주제)도 상자와 선 이상의 표현으로 그릴 수 있게 한다.
3. AI가 사양만 쓰면 위 두 가지를 기본값으로 얻게 한다. 장면 코드를 손으로 짜는 일은 예외로 만든다.

**비목표**
- 런타임 기반 교체(프레임워크, 외부 라이브러리, Lottie/Rive 도입). Confluence 매크로 규칙(인라인 스크립트 1개, 외부 요청 없음)과 충돌한다.
- 마우스·스크롤에 반응하는 인터랙션. 문서 속 그림이므로 범위 밖이다.
- 물리 시뮬레이션과 무작위 움직임. 결과를 예측할 수 없고, 데이터 시각화에서 무작위는 정직성 문제가 된다.

## 2. 현재 구조와 문제 (실측)

```
사양 JSON ─▶ visual_spec.py (검증·모델·이벤트·캡션) ─▶ data ─▶ scenes/*.js  draw(T, geom)
                                                              │       (T의 순수 함수)
                                                              ├─▶ 브라우저: runtime.js가 T를 진행
                                                              ├─▶ Node: 같은 코드로 정적 그림 (JS 없는 환경, 인쇄)
                                                              └─▶ visual_gates.py: 겹침·대비·높이·모델 일치·움직임 속도
```

**지켜야 할 불변식 (바꾸지 않는다)**
- 장면은 T의 순수 함수다. 덕분에 이동(seek), 되감기, 인쇄, Node 정적 그림, 모델과의 일치 검사가 된다.
- 숫자는 Python 모델에서만 나온다. 캡션은 모델 이벤트에 묶인다.
- 매크로 하나에 인라인 스크립트 하나, 외부 요청 없음.

**문제 1. 움직임이 코드 곳곳에 흩어져 있다.** 장면·문법 14개 파일 중 9개가 `(T-t0)/0.45` 같은 시간 계산을 직접 한다.
공용 이징(`K.ease`)을 쓰는 곳은 1곳뿐이다. 길이 상수(0.25, 0.35, 0.45, 0.7 …)도 파일마다 다르다.
결과적으로 같은 종류의 문제가 사례마다 다시 생긴다(0.10.1의 2·9·10번 지적, 0.11.0에서 추가로 찾은 3건).

**문제 2. 상태 전환이 한 프레임에 일어난다.** 다이어그램 단계가 바뀌면 선 색, 굵기, 단계 목록 강조가 같은 프레임에 바뀐다.
연쇄 장애의 서버 상태, 상태줄 숫자도 마찬가지다. 검사는 이것을 잡지 못한다(0.11.0에서 픽셀 기준으로는
원본과 구분되지 않아 검사에서 뺐다. 픽셀이 아니라 "선언된 속성"으로 봐야 잡을 수 있다).

**문제 3. 개념을 그릴 어휘가 없다.** 종류는 데이터 차트(flow, trend, bars, share, timeline, distribution)와
상자·선 다이어그램뿐이다. DDD 글의 시각화가 단순해 보인 직접 원인이다.

## 3. 제안 구조

```
            ┌──────────────────────────────────────────────────────────────┐
 L4 (신규)  │ 개념 어휘: 영역·주체·문서·이름표·쌓임·전환 … (concept 종류)   │  3단계
            ├──────────────────────────────────────────────────────────────┤
 L3         │ 종류·장면: 배치(geom)와 그리기. 시간 계산을 직접 하지 않는다   │
            ├──────────────────────────────────────────────────────────────┤
 L2 (신규)  │ 안무(choreography): 큐(cue) 선언 → 절대 시각으로 해석 → 값 평가 │  2단계
            ├──────────────────────────────────────────────────────────────┤
 L1 (확장)  │ 키트: 그리기 부품 + 움직임 수학(이징 세트, 닫힌 식 스프링·접근)   │  1단계
            ├──────────────────────────────────────────────────────────────┤
 L0 (유지)  │ 런타임: 시계, 재생 배율, 컨트롤, 인쇄, 축소 모션                  │
            └──────────────────────────────────────────────────────────────┘
```

### L1. 움직임 수학 (키트 확장)

모두 **닫힌 식**이다. 같은 T에는 같은 값이 나온다. 매 프레임 값을 누적하는 방식(원문의 지수적 접근·스프링 구현)은
순수 함수 조건을 깨므로, 같은 느낌을 내는 해석해로 바꾼다.

| 부품 | 식 | 용도 |
|---|---|---|
| `K.curve.out / in / inOut / linear` | cubic-bezier 근사 | 등장은 out, 퇴장은 in, 이동은 inOut, 일정한 흐름은 linear |
| `K.spring(u, {zeta, freq})` | 1 − e^(−ζωt)·(cos ω_d t + (ζω/ω_d)·sin ω_d t) | 강조(단계 시작 시 살짝 커졌다 돌아옴). **데이터 위치에는 금지** |
| `K.approach(from, to, t, k)` | to + (from − to)·e^(−k t) | 숫자·게이지가 새 값으로 미끄러짐. 수렴 시간 ≤ 0.4초로 제한해 실제 값이 가려지지 않게 |
| `K.wave(t, amp, freq, phase)` / `K.saw(t, period)` | 사인 / 톱니 | 대기 중 표시처럼 의미 있는 주기만. 장식용 상시 깜빡임 금지(가이드라인 유지) |
| `K.mix(c1, c2, u)` | 색 보간 | 상태 색 전환을 한 프레임이 아니라 곡선으로 |

### L2. 안무 층 (핵심 변경)

움직임을 코드가 아니라 **데이터(큐 목록)** 로 선언한다. 원문의 "그래프를 먼저 나눠 설계하라, 파이프라이닝,
속성 분리"를 구조로 만든 것이다.

**큐 형식 (사양 또는 종류의 기본값에서 생성)**
```json
{"target": "node:gw", "prop": "emphasis", "from": 0, "to": 1,
 "at": "step:2", "offset": 0, "dur": 0.35, "curve": "out"}
```
- `target`: 장면 안의 요소 id (`node:*`, `edge:*`, `label:*`, `group:*`, `value:*`).
- `prop`: `opacity`, `emphasis`, `color`, `progress`(선 그리기), `pos`, `scale` 등 종류가 지원하는 속성.
- `at`: 모델 이벤트 이름 또는 시각. **이벤트 기준**이라 캡션과 같은 시계에 묶인다.
- 조합 도구: `seq`(앞이 끝나면), `overlap`(앞이 80% 지났을 때), `stagger`(여러 대상에 간격을 두고), `parallel`.

**어디서 계산하나**
- **Python(visual_spec)**: 이벤트 → 절대 시각 해석, seq/overlap/stagger 전개, 검증(길이 범위, 금지 조합).
  테스트하기 쉽고, 캡션 속도 계산(paced_rate)과 같은 곳에서 시간을 다룬다.
- **JS(키트)**: `C.v(target, prop, T)`가 해석된 큐를 평가한다. 장면은 이 값만 받아 그린다.
- 장면 파일은 `(T-...)` 같은 시간 계산을 직접 하지 않는다(단위 테스트로 금지. 이미 이전된 장면부터 적용).

**종류의 기본 안무**: 사양에 큐를 쓰지 않아도 종류가 기본 안무를 만든다. 예: 다이어그램 단계 전환 =
이전 단계 강조 해제(in, 0.25초) → 0.8 지점에서 새 단계 선 그리기(out, 0.35초) → 상자 강조(spring) → 목록 항목 색 전환(0.2초).
사양 작성자(AI)는 기본값을 받고, 필요할 때만 덮어쓴다.

### L3. 종류·장면

- 배치(geom)와 그리기만 한다. 값은 L2에서 받는다.
- 기존 장면은 그대로 동작한다. 단계적으로 이전하며, 이전한 장면부터 "직접 시간 계산 금지" 검사를 켠다.

### L4. 개념 어휘 (3단계, 레퍼런스 비교 후 확정)

kciter.so의 개념 설명 글("바보야, 문제는 경계야!" 캔버스 17개, "클로드 블루" 7개, "메인 스레드" 5개)을 같은 폭으로
캡처·비교해 **반복되는 표현**을 뽑는다. 지금 예상하는 후보(비교 후 확정·삭제):
- 영역(boundary): 안팎 구분, 경계를 넘을 때의 변환
- 주체와 문서(actor/document): 누가 무엇을 들고 이동하는가
- 이름표(label set): 같은 대상이 영역마다 다른 이름을 갖는 장면(DDD 바운디드 컨텍스트)
- 쌓임과 분할(stack/split): 큰 일이 쪼개지거나 쌓이는 장면
- 전후 대비(contrast): 같은 장면을 두 조건으로 나란히

이것들을 L1~L2 위에서 조립하는 `concept` 종류를 추가한다. 다이어그램 종류의 배치 규칙과 검사를 재사용한다.
레퍼런스의 데모 코드와 그림은 옮기지 않고, 표현 방식만 참고한다.

## 4. 움직임 규칙 (원문 원리를 우리 기준으로 구체화)

| 상황 | 곡선 | 길이 | 비고 |
|---|---|---|---|
| 요소 등장 | out | 0.3–0.45초 | 투명도 + 짧은 이동(≤ 8px) |
| 요소 퇴장 | in | 0.2–0.3초 | 등장보다 짧게 |
| 위치 이동(토큰 제외) | inOut | 거리 / 공용 속도 | 공용 속도 `K.M.speed`(0.11.0) 유지 |
| 상태 색 전환 | out | 0.2–0.3초 | `K.mix` |
| 강조 | spring (ζ≈0.6) | ≈0.4초 | 크기 최대 +6%. 데이터 위치 금지 |
| 숫자 변화 | approach | 수렴 ≤ 0.4초 | 최종값은 모델 값과 정확히 일치 |
| 여러 개 등장 | stagger | 항목당 40–80ms | 전체 ≤ 1.2초, 넘으면 묶어서 |
| 단계 전환 | overlap 0.8 | — | 앞 동작이 끝나기 전에 다음 시작 |

축소 모션(prefers-reduced-motion), 인쇄, JS 없는 환경은 지금처럼 최종 장면을 보여 준다(변경 없음).

## 5. 검사 (측정 가능한 것만)

L2가 생기면 픽셀이 아니라 **선언된 큐**를 기준으로 검사할 수 있다.

| 검사 | 기준 | 비고 |
|---|---|---|
| 순간 전환 | 이전된 장면에서 opacity·color·emphasis가 한 프레임에 0.5 이상 바뀌면 실패 | `cut: true`로 의도적 컷을 선언하면 예외 |
| 동시 등장 | 같은 프레임에 4개 넘게 등장하면 stagger 요구 | |
| 숫자 건너뜀 | 상태줄·라벨 숫자가 approach 없이 바뀌면 실패 | 최종값은 모델과 정확히 일치해야 함(기존 검사 유지) |
| 데이터 오버슈트 | 데이터 위치를 나타내는 속성에 spring 사용 시 빌드 오류 | Python 검증 단계 |
| 길이 범위 | 표 4의 범위를 벗어나면 경고 → 2단계 끝에 오류로 | |
| 기존 검사 | 겹침·대비·높이·모델 일치·토큰 속도·직각 배선 | 그대로 |

검사가 판단하지 못하는 것: 움직임이 "자연스러운가", 개념이 "잘 전달되는가". 전후 비교 화면을 사용자에게 보여 판단을 받는다.

## 6. 단계와 완료 조건

| 단계 | 범위 | 완료 조건 |
|---|---|---|
| 1. 움직임 수학 | L1 부품, 기존 장면의 시간 계산을 부품으로 교체(동작 변화 최소) | 단위 테스트(곡선 경계값, 닫힌 식 = 수치 적분 근사), 기존 검사 전부 통과 |
| 2. 안무 층 | 큐 형식, Python 해석·검증, JS 평가, 다이어그램·분포·연쇄 장애부터 이전, 큐 기반 검사 | 이전한 장면이 새 검사 통과, 옛 버전(7cc0df3)의 2번 문제를 새 검사가 잡는지 확인, 전후 비교 화면 사용자 검토 |
| 3. 개념 어휘 | 레퍼런스 캡처·비교표, 부품 확정, `concept` 종류, DDD 그림 재작성 | 비교표 사용자 검토, DDD 3개 전후 비교, 레퍼런스에 없던 새 주제 1~2개를 처음 한 번에 통과하는지 시험 |

각 단계 끝에 결과를 보여 드리고 다음 단계 진행 여부를 결정한다. 1단계 결과가 약하면 2단계 설계를 다시 본다.

**파일 영향(예상)**
- 1단계: `visuals/live/kit.js`, 장면·문법 9개 파일, `tests/test_live_runtime.py`
- 2단계: `scripts/visual_spec.py`(큐 해석·검증, 별도 모듈 `scripts/choreo.py`로 분리 권장), `visuals/live/choreo.js`(신규, 코어 파일에 포함),
  `scripts/visual_gates.py`, `references/visual-specs.md`, `references/live-runtime.md`
- 3단계: `visuals/live/scenes/concept.js`(신규), 사양 문서, 예제

## 7. 결정이 필요한 점

1. **큐를 사양에 노출할까?** **확정(사용자 승인): 권장안대로.** 권장: 종류 기본 안무만 쓰고, 사양에서는 `motion` 수준(`calm`/`default`) 정도만 고르게 한다.
   큐 직접 작성은 맞춤 장면용으로만 연다. AI가 매번 안무를 짜면 결과가 들쭉날쭉해진다.
2. **검사 강도:** **확정: 권장안대로.** 권장: 2단계 동안은 경고, 이전이 끝난 종류부터 실패로.
3. **3단계 범위:** 개념 부품을 몇 개까지 만들지는 비교표를 본 뒤 결정. 사람이 글마다 만든 장면의 완성도를 부품
   조합으로 얼마나 따라갈 수 있을지는 아직 모른다. 못 따라가는 부분은 맞춤 장면으로 남기고 문서에 적는다.
4. **움직임 수치(표 4):** 제 판단으로 정한 값이다. 레퍼런스 데모의 실제 길이를 측정해 보정할지(캡처 시 측정 가능) 결정 필요.
   권장: 3단계 캡처 때 함께 측정해 보정.

## 8. 진행 기록

**1단계 (v0.12.0) 완료.** 키트에 `K.CURVE`(linear/out/in/inOut), `K.DUR`, `K.tween`, `K.spring`, `K.pop`, `K.approach`,
`K.stagger`, `K.wave`, `K.saw`, `K.mix` 추가. 장면의 시간 계산을 둘로 나눔: 데이터 보간(부하, 진행률, 선 값)은 모델을 따르므로
그대로, 표현용 움직임(분포의 꼬리 띠·떨어지는 점·백분위 선, 이벤트 루프의 큐 당김·I/O, 스레드 풀의 칸 등장·깜빡임·큐 당김,
흐름의 거부 토큰, 다이어그램 토큰)은 공용 곡선으로 옮김.
- 발견: 처음 고른 inOut(0.4,0,0.2,1)은 순간 최대 속도가 평균의 약 2.4배라, 다이어그램 토큰(561px/s)과 스레드 풀 큐(537px/s)가
  0.11.0 속도 검사에 걸렸다. inOut을 대칭 smoothstep(최대 1.5배)으로 정함. 기존 검사가 새 부품의 부작용을 잡은 사례.
- 검증: 단위 테스트(곡선 경계·단조성, 닫힌 식 스프링 = 수치 적분 ±0.002, approach가 settle 뒤 정확히 목표값, tween 순수성),
  라이브 18/18 × 2폰트, 예제 15/15 × 2폰트, 모니터링·스모크 통과.
- 화면 변화는 작다(곡선 모양만 바뀜). 1단계의 효과는 부품과 기준을 한곳에 모은 것이고, 눈에 띄는 개선은 상태 전환을
  큐로 다루는 2단계에서 나온다.

**2단계 (v0.13.0): 안무 층, 다이어그램부터.** `scripts/choreo.py`(큐 생성·검증: 속성별 길이 범위, 겹침 금지,
연속성, 최종 장면 전 완료), `visuals/live/choreo.js`(평가기, 코어 파일), 다이어그램 기본 안무(이전 단계 흐려짐 0.25초 in →
80% 지점에서 새 경로·상자·목록 상승 0.3초 out, 상자 강조 1회, 토큰도 상승과 함께 출발, 마지막 0.5초에 최종 장면으로 정착).
- 검사: `data-k` 요소의 색(채널 차 > 128/255) 또는 선 굵기(> 0.6px)가 한 프레임에 바뀌면 순간 전환. 이전한 종류(다이어그램)는 실패,
  나머지는 경고(결정 2).
- 검사 확인: 같은 다이어그램에서 큐만 제거하면 실패(e0 굵기 2.4→1.8 등), 큐가 있으면 통과.
- 남은 2단계 대상: 연쇄 장애 서버 상태, 상태줄 숫자(approach), 추이 이벤트 라벨, 분포 표식, 흐름·스레드 풀 상태색.

**2단계 마무리 (v0.14.0).**
- 큐 길이를 화면 기준 초로 바꿈(`choreo.cue(..., rate)`, JS `K.wall`). 모델 시간 기준이던 v0.13.0의 다이어그램 전환은
  실제 화면에서 약 1.6초였다(보고 정정). 연쇄 장애는 캡션 구간에서 재생이 느려져 모델 0.35초가 화면 1.5초가 되는 문제로 발견.
- trend: 같은 순간에 드러나는 것(이벤트 선, 라벨, 주석, 구간, 로그)이 차례로 들어온다(스태거 ≤ 0.24초, 등장 0.4초).
  선은 위에서 내려오고, 알약과 메모는 이전 것이 나간 뒤 새것이 들어온다(`K.swap`). 끝 시각의 등장에는 정착 꼬리(`time.settle`).
- 연쇄 장애: 카드 경고·실패·제외 수준, DB 느려짐이 큐. 상태 문구 교체, 실패 순간 경보 펄스 2회(`K.saw`),
  몫 비율과 DB 지연은 `K.approach`.
- 흐름: 대기열이 생기고 빠지는 시각(모델)으로 병목·게이지·대기 상자·여유 알약이 섞인다(`choreo.switches`가 짧은 깜빡임 제거).
  스레드 풀: DB 느려짐·회복이 큐, 의존 점은 이동 거리로 위치를 계산해 속도 변경 때 튀지 않는다.
- 새 검사가 찾은 것: 한 프레임 등장(이벤트 선 투명도 3배 속도, 끝 시각 등장, 대기 상자·라벨), 올라오는 라벨과 값 라벨의 겹침,
  흐름 토큰 id 중복(같은 도착 시각, 두 레인) → 전부 수정. 주석 시각 검사는 "화면 0.6초 안에 등장"으로 완화(미리 보이면 여전히 실패).
- 상태줄 숫자는 그대로 둠: 정수 개수이고, 검사가 모델 값과 정확히 같은지 확인하므로 미끄러지는 표시가 맞지 않는다.
- 분포 표식은 v0.10.1에서 이미 선 그리기·라벨 등장 처리(이번에 키·검사 대상으로는 넣지 않음).

## 9. 위험

- 2단계는 장면 코드를 많이 건드린다. 이전 중에도 기존 검사 전체를 매번 돌리고, 장면 하나씩 커밋한다.
- 안무가 화려해지면 오히려 산만해질 수 있다. 가이드라인의 "장식 금지, 한 블록에 하나의 주장"은 유지하고,
  강조(spring)는 단계 시작에만 쓴다.
- 레퍼런스 캡처는 로컬(`dist/`)에만 두고 커밋하거나 공개하지 않는다.
